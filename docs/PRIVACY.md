# Privacy: what the extension keeps, where, and why it asks for each permission

TailorIT Autofill fills job applications from a profile the person keeps in their own TailorIT. It submits an application only on the person's own click on Submit application in its panel, with Submit set to Auto under Modes (v3 Phase 4), or, with Run auto-apply turned on, for a job the person queued in TailorIT (v3 Phase 5); it never logs a field value, keeps the resume and the cover letter only for the seconds it takes to attach them (or to show their preview: since v1.5 in a window over the page the person is on, inside a frame of the extension's own that the page's scripts cannot read, and in a full-window page of the extension's own where none can show; in v1.4 always that full-window page; before it in its panel), and decrypts a job-site password only for the one sign-in it is typed into (Sign-in Auto, v3 Phase 5: until jr6 read from TailorIT; since jr6 the one the person sets in the extension's own settings, Sign-up Information, kept in this browser, the password encrypted, never sent to TailorIT). Since v1.3, once a site confirms an application the person submitted, it sends that application's questions, and (unless they turn it off) their answers, to their own TailorIT, which never gives the answers to an AI; the extension keeps none of them. Since v1.4, on the person's click, it asks their TailorIT to tailor a resume and a cover letter for the job. Since v1.5 it also fills a question from an answer their TailorIT prepared for the job ahead of time (Prebuild), where the profile and their own earlier answer to that job leave it open, and its preview page is its one web-accessible resource, at an address that changes each browser session. Since v1.5 part 2, on the person's Start in its panel's Queue tab, it opens the jobs they queued in their TailorIT one by one in new background tabs, on the timer they set, fills each and submits it as their own settings say (Submit only with Submit on Auto), and tells their TailorIT as each opens and how each went; it keeps no job's address, and never runs beside Run auto-apply. Since jr6 (the owner's words of 2026-11-10) its panel's Autofill, on a job page that shows no form, presses the site's own Apply and the steps the site shows on the way, in the same tab and on the same site, and fills what opens; and at a site's email-first step it types the person's email in either Sign-in mode, pressing its Next only on Sign-in Auto or with Sign Up & Autofill. This file is the source for the store listing's privacy answers and permission justifications.

## The page-world bridge

To choose an option in a page's React dropdown as the page's own code does (docs/SPEC-AMENDMENTS.md §12), the extension runs one small script in the page's own world on the ATS hosts, beside the content script, which runs apart from the page. It holds nothing: no profile, no answer, no token, no setting, no state but the one listener it waits on, and it reaches no part of the extension (no messaging, no storage, no browser API, no network).
- **The page sees everything it is told.** The page's own scripts fully control the world the bridge runs in: they can read every request, change how the bridge behaves and answer in its place. So nothing is sent there that the page should not read.
- **What it is told:** for each dropdown answer, which option to choose (its label, as the extension read it from the page), whether the dropdown takes several answers, what kind of request it is, and a random id. The label reveals the answer the fill is choosing exactly as the filled form will show it to the page, a moment earlier. Asked about a field, the bridge answers that field's type and path as the page's own code names them (two short strings), never a value.
- **The field question on Ashby:** Ashby's adapter asks the bridge what each of the page's dropdowns is (its `react.field` request: the request and its random id, nothing of the person's), to tell a Location search from a list. The page's scripts can see that request whenever the extension reads the form, a dry run's reading included, and so learn that the extension is reading it; it carries no answer, and nothing is written.
- **What it never gets:** any profile value, typed answer or anything else of the person's. The content script writes those as before, and a remote search's typed query still goes into the page's text box as before; the bridge only chooses an option the page lists.
- **What the page can do with it:** read its requests, send it requests of its own (which can only make it choose one of the page's own options on that page), and tell, from the moment it loads, that the extension is installed, since the bridge acknowledges a request. Its answers are never trusted: the content script reads the page back itself.
- **Where it is there at all** (the v3 Phase 6/7b review, and its round 2): it is read from the frame's own address before any script of the page runs (`src/adapters/bridge-address.ts` `bridgeInstallsAt`, which `src/adapters/address.ts` re-exports).

## The page-world submit watcher (v5 Phase 2)

To learn that an application went through on platforms whose page after submitting no snapshot of ours shows, the extension runs a second small script in the page's own world (`src/page/submit-watch.ts`; docs/SPEC-AMENDMENTS.md §15, PLAN decision 14, written in our own code after Jobright's observed behaviour). Like the bridge it holds nothing and reaches no part of the extension (no messaging, no storage, no browser API, no network of its own).
- **Where it is there:** a static content script on the candidate hosts of Workday (`*.myworkdayjobs.com`, `*.myworkdaysite.com`, `*.myworkdayjobs-impl.com`), ClearCompany (its `/careers/` pages), Oracle Recruiting Cloud (its Candidate Experience on `*.oraclecloud.com` and `*.fa.ocs.oraclegovcloud.com`) and SuccessFactors (`*.successfactors.com`, `*.successfactors.eu`), from the moment the page starts loading. It installs on those hosts' candidate pages: a posting or its application form, as the bridge reads them, and (since the Phase 2 review) anywhere under the candidate app's own path where the site is a single-page app a person enters at a job list (Oracle's `/hcmUI/CandidateExperience/`, Workday's `myworkdaysite.com/[<locale>/]recruiting/<tenant>/<site>`, ClearCompany's `/careers/`; on a Workday tenant's own host, any page). It is never on an employer's other pages on those domains, nor in a frame an employer's own page holds, and elsewhere it does nothing at all. Until a Submit is pressed in that page, nothing it tells is listened to. On an employer's own domain that shows Oracle's Candidate Experience (recognised by its address and the app's own markup while Company career sites act: "Filling (v5 Phase 2)" below), the worker runs it in that page's own world only once the content script found Oracle's application form there, once per page. A request the page sent before then is not seen; the person can still mark the job applied themselves.
- **What it does:** on Workday, ClearCompany and Oracle it wraps the page's own `fetch` and `XMLHttpRequest`: each request goes through unchanged, with what the page gave it, and the page gets its answer unchanged (nothing delayed, retried or added). Of each request it reads the method and the address, to tell the one that sends the application; of that one's answer, its status and whether it was redirected; never a header. On SuccessFactors, whose request answers alike whatever happened, it wraps the page's own function that sends the application, once the page has made it, and still calls the page's own callback with the site's own result.
- **The one fact it reads of a body** (the owner's word of 2026-11-08 on Jobright's behaviour): on Workday, from a copy of the send request's answer, whether it names the application and holds no error; on Oracle Recruiting Cloud, from the request's own body, whether it is the application's create or confirm step for the posting the page's address shows (a candidate named), and from a copy of its answer, whether the site created or confirmed it; on SuccessFactors, from the call's own details (and the posting's id in the page's address or form), whether it is this posting's new application, and from the site's result, whether it says the application was taken. ClearCompany's bodies are never touched: its status alone. A body is read only for that yes or no, at most 64 KiB of it, and dropped at once; those bodies hold the person's details (a name, an email, answers) as the page's own requests do, and none of it is kept, logged or passed on.
- **What it tells:** only which of the platform's signs it saw: an event on the document whose detail is the sign's name alone (`workday-finalize`, say), never an address, an id or a value. The extension takes it only after a Submit was pressed in that same page, in the platform's order, and while the page shows no error; the worker takes it only from the frame and page that pressed; then TailorIT's tracker is told Applied, as for any other confirmation.
- **What the page can do with it:** tell that the script is there (its `fetch` is no longer the browser's own), as it can tell the bridge is, from the moment it loads; since it wraps `fetch` and `XMLHttpRequest` from the moment the page starts loading (so the site cannot keep its own copy first), any script on those candidate pages, the job lists included, can tell the extension is installed without any fill or click. PLAN decision 14 accepts this, as Jobright's own wrappers do; the review's M3 needs the early install. A page can also forge a sign, as it could draw a confirmation message, which is why a sign counts only after a Submit pressed in that page. On an employer's own domain the sign alone never counts: the page must also show that Oracle's app left its application form (its own frame kept, its Submit gone). `scripts/check-build.mjs` holds the script to its hosts, to never naming a header, storage or the extension's APIs, and drives it with answers that hold a person's details to show that only the sign leaves.

## The page patches (v5 Phase 2)

Once a fill starts on a page, the extension runs a third small script of its own in that page's own world (`page-patches.js`; PLAN decision 14, Jobright's alert suppressor and file-picker interception in our own design). It is no content script: the worker runs it in one document, as the first fill that writes begins there (never a dry run), only for a frame of ours that holds a form, at most twenty times a minute per frame. It holds no data and reaches no part of the extension (no messaging, no storage, no network: `scripts/check-build.mjs` refuses a bundle naming any of them); it adds one listener on the document for the extension's commands and changes nothing until a write asks. A page where no fill ran holds none of it.
- **The page's dialogs during a write:** right before each of its writes, the extension has it put the page's `alert` and `confirm` behind wrappers, and right after, put them back as they were. While it waits on the page after a write (an upload, a picker's press, a date's parts) only the `alert` is held (since the Phase 2 review): a page's `confirm` is held only through a write's own synchronous events, never through a wait, so a question the page asks meanwhile ("Stay signed in?") always reaches the person as the browser's own dialog. While held, an alert the page shows returns as if closed, and a confirm as if the person chose Cancel; each is counted, never its words. A dialog that follows the person's own click or key is never held: a write's own events leave no room for one, and during a wait the person's own pointer or key on the page ends the hold at once. A hold never released ends by itself after 12 seconds. Since the review the person sees the counts, in a TailorIT notification on the page ("The page showed 1 message while Autofill filled it…"; none under "TailorIT notifications on the page: Never show them"): counts only, never the page's words; they are logged too, as before.
- **The site's own file picker** (no site's adapter declares such a button yet, so today it never acts): for a résumé button an adapter declares, one with no file input in the form, the extension arms it for that one press, and the page's own opening of a file chooser is answered instead of shown. Where the page clicks a file input, that input is named back to the extension, which puts the chosen résumé into it as any upload does; since the Phase 2 review only a file input that belongs to the pressed button (inside its own part of the page, as its adapter declares it or the button's parent, or one made at the press and never put in the page) can receive it, and any other file input's click opens the page's picker as always. Where the page asks for the browser's file picker (`showOpenFilePicker`) during the arm, the script answers with that one file. Either way the résumé reaches only the page it is being uploaded to, as the upload itself would hand it over; the person's own pointer or key on the page during the wait disarms it at once, and what the arm shadowed is put back after its first use or two seconds.
- **What the page can see:** the wrappers while they stand, and, once a fill ran, that the script is there (it answers its commands); a page can forge a hold, which only keeps its own dialogs from showing, or claim a file input during an arm, which only puts the résumé into an input of that same page (since the review, inside the pressed button's own part of it), or call `showOpenFilePicker` during an arm, which hands it the résumé the upload was about to hand it.

## Forms that save as they are filled (Ashby)

Ashby's application form saves every answer to Ashby's own server about half a second after it is written, and again when the field is left, before anything is submitted (the live capture of 2026-11-01: each change is a `POST` to Ashby's `ApiSetFormValue`). A file put into an upload question is uploaded to Ashby the moment it goes in (`ApiCreateFileUploadHandle`, then the file). Its SMS consent is sent to Ashby the moment one of its two answers is chosen. The page does this for a person's typing too; the extension neither causes nor stops it.
- **So a fill reaches Ashby at once, before Submit.** Every answer the extension writes on an Ashby form is in Ashby's hands within about a second, whether or not the person then submits: the profile's answers, and, under the owner's policy (the AI fills everything, its drafts accepted by default), the AI's answers, its drafts and its best guesses too.
- **Files at once.** The resume, and a cover letter (the AI's letter included, when TailorIT's AI wrote it), are uploaded to Ashby's server the moment the extension puts them into the form, before Submit. The extension then waits for Ashby to show the file uploaded (its name with its Delete file button), at most 10 seconds; a file Ashby says failed to upload, or never shows uploaded, is flagged for the person, never verified.
- **Nothing to undo there.** The extension's final check can put a field back as it was once the run ends (its guard's revert), but Ashby has already saved what was written; Ashby saves the reverted value the same way. Nothing is ever submitted, and the person can still change or clear an answer before they submit, which Ashby saves the same way.
- **Drafts held back on request** (until v4, whose settings version 6 dropped the setting: every draft is written)**.** With the setting that keeps AI drafts for the person's confirmation on, an AI draft is not written into an Ashby form at all until the person confirms it in the panel (Confirm draft): until then it stays in the extension's memory, and Ashby sees nothing of it. A field the person typed into meanwhile is theirs, and the draft is dropped.
- **A month sets this year first.** Choosing an Education block's month makes Ashby choose this year in its year list too (and save it), until the extension chooses the year a moment later; a run stopped between the two leaves this year saved.
- **A dry run writes nothing,** so nothing of the person's reaches Ashby: no field is typed into, nothing is chosen or clicked, no file is put in. (The bridge's field question above is a reading, and is asked in a dry run too.)
- **Never pressed:** Ashby's "Autofill from resume" (which uploads a resume to Ashby's server and rewrites the form from it), its Upload File and Delete file buttons, and an Education block's Delete. Submit only on the person's click on Submit application in the panel, or with Submit on Auto (v3 Phase 4).
- **The SMS consent follows the Consent boxes mode** (v3 Phase 3). Under All agreements, the default, its Yes ("given") is chosen like every agreement on the form, and choosing it sends the consent to Ashby at once (`ApiSubmitCandidateTextingConsent`), before Submit. Under Required only it is optional and not pre-approved by default, so it is left unanswered (since v4 decided, never left for the person) and nothing is sent.

## The auto-apply agent (v3 Phase 5)

The owner's decision (docs/SPEC-AMENDMENTS.md §12 Decision 9): with Options › Auto-apply › "Run auto-apply" on (off by default, turned on only after the person confirms, once, that applications go out unattended with AI-guessed answers), the extension applies by itself to the jobs the person queued in TailorIT.
- **What it asks TailorIT:** its next job (GET /agent/next, scope `agent:run`), at most every 30 seconds while it is on and a browser window of the person's is open, waiting a minute, then five, while the queue is empty or TailorIT cannot be reached. TailorIT answers the job's id, title, company, its application form's address and the resume to attach, and binds the job to this browser's connection until it reports.
- **What it does:** opens that address (only a canonical application address on Greenhouse's job-boards.greenhouse.io, Lever, Ashby or Workable's apply.workable.com, since TailorIT's API 4, and, since its API 6, an iCIMS posting's page or a Pinpoint form, that the extension fills; anything else is reported failed, unsupported site, and never opened) in a new window of its own, which Chrome is asked to open unfocused; fills only the form of that job's own application (another posting's page in its tab, or a page naming none, ends the job unfilled) exactly as Autofill does, with every rule above (the profile, the AI help as the settings allow, the agreement boxes, the cover letter and the resume TailorIT named for the job); presses Next and Submit by itself, Submit once per job (once it was pressed, a form shown again in another document gets Submit on Manual and no run, and the job waits for the site's confirmation); presses a posting page's own Apply (or Ashby's Application tab) when the page shows the posting first; signs in only as the person's Sign-in mode says. At a posting that forbids AI with "Ask me each time" chosen (until v4, which removed that choice), nobody is there to answer, so it fills from the profile only and its skip rule decides.
- **What it tells TailorIT:** how the job went (POST /agent/:id/result: submitted, skipped, needs you or failed, a reason from a closed list, and how many answers were AI guesses, a count). A submitted job is marked Applied by TailorIT with that result (the extension does not also call POST /applied for it). The result carries no value, question or answer; since v1.3, once TailorIT took a submitted result, the application's questions and (unless the person turned it off) answers go to it as for any application the person submits ("A submitted form's questions and answers" in the data inventory).
- **When it stops and leaves a job for the person:** a check that the person is human, a bot check, an email code, a sign-in it cannot do, a required field still empty, a posting that forbids AI (with those two skip rules on, the default), a legal answer that was the AI's guess (with that rule on, off by default), errors the page still shows after one retry, a closed posting, a page that does not load, ten minutes without progress (25 in all), the person closing its tab or its window (their Stop, which also pauses the agent until they turn Run auto-apply on again), Stop, Run auto-apply turned off, the disclosure changing, the connection losing `agent:run`, or the connection changing or going (which also turns Run auto-apply off and asks for the person's confirmation again). It then lets go of its tab (its run cancelled, the person's own settings back) and closes that tab only, never a window and never a tab already gone. The job stays listed in TailorIT's Auto-apply page for the person. A result TailorIT cannot take yet is kept and sent again (a submitted one for every answer but 404 and 400), and the status says "a result not yet told TailorIT" until it is.
- **A checkbox CAPTCHA** (the snapshot build of 2026-11-06, the owner's decision): where the only challenge on the page is an "I'm not a robot" box not yet solved (reCAPTCHA's or hCaptcha's checkbox), a run fills the form, as Autofill does, but presses nothing (no Next, no Submit, no entry, no sign-in) and never touches the box (its response field is only read for being empty, and is never a field of the form); at Submit the agent leaves the job for the person (needs you, captcha), who ticks it and submits. A challenge that pops up (an image grid) pauses everything before anything is filled, as always. Since v5 Phase 1 (like Jobright) the run presses beside the unticked box (Next, Submit, the entry, the sign-in), still never touching it, and the site decides: a press the site refuses for the check, or its "complete the CAPTCHA" error, leaves the job for the person as needs you, captcha (nobody watches the agent's window to tick it). A pop-up challenge still pauses everything.
- **Outages** (the audit of 2026-11-06): a page that never loads is never reported as a closed posting; while the browser is offline no job is taken; and when Chrome opens no window, or three jobs in a row end with a page that never loaded, the agent pauses itself (Run auto-apply off, the reason in its status, the person's confirmation kept) rather than empty the queue into failures.
- **A window in the background:** Chrome slows the timers of a page in a window behind others (intensive throttling, after about five minutes hidden), which can stretch the fill's waits for the AI's answers. A run still at work counts as progress, so only ten minutes with neither a new report nor a run at work, or 25 minutes in all, ends the job (timed out).
- **Who can start it:** only the person, in the options page; its commands come only from the extension's worker, with its own token, after its own look at TailorIT. No page, frame or message from a page (TailorIT's own pages included, which may message the extension for pairing alone) can start it, choose its job, make it submit or learn the password.
- **The `alarms` permission** wakes the worker every 30 seconds while it is on, or while a result waits to be told (the browser stops an idle worker after about 30 seconds); otherwise no alarm is set.

- **Never beside Run auto-apply:** Start turns Run auto-apply off (its running job left for the person); turning Run auto-apply on stops a running or paused queue first; and TailorIT never hands a job one run took to the other, nor to another browser. A changed or dropped connection stops the queue; its results wait for a connection to tell them.
- **The worker's wake-ups:** the `queue-tick` alarm (the `alarms` permission), every 30 seconds while the queue runs, one of its tabs waits for its page, or one of its results waits to be told; none otherwise. A run lives in `chrome.storage.session`, so a worker the browser stopped picks it up; a browser restart ends it (its tabs' ids name nothing then).
- **New messages** (the panels and the worker only; on a job page, only the panel on the page's own views, "The panel on the page" above): `queue/status` (the phase, counts, seconds and why it waits or stopped: value-free), `queue/list {offset}` (50 jobs at a time: titles and companies as TailorIT named them, statuses and reasons, whether a tab is open), `queue/start`, `queue/stop`, `queue/pause`, `queue/resume` (each answering the status; each a trusted click on a control shown 600 ms), `queue/focus {id}` (the job's tab to the front) and, to the panels, `panel/changed 'queue'`. Logs: counts, phases and places in closed lists only (`queue.started`, `queue.opened`, `queue.open-failed`, `queue.fill-started`, `queue.finished`, `queue.report-failed`, `queue.read-failed`, `queue.paused`, `queue.resumed`, `queue.stopped`, `queue.done`), never an id, an address or a title.
- **Permissions: none added.** The manifest is unchanged. The tabs need none (`chrome.tabs.create`, `update`, `get` for whether the tab is still there and its window shows it, and `remove`, of the queue's own tabs; `chrome.windows.update` to bring one to the front); of a queued tab no page of ours spoke from within 60 s, the worker reads from Chrome what kind of page its address is (a posting or the site's other page: posting closed or page error), keeping nothing of it; the `alarms` permission (v3 Phase 5) wakes it.
- **Since jr6** a queued job whose Autofill was given at a page with no form (the posting's own Apply, an entry choice, an account wall) and whose tab no run has reported from 90 seconds later is Ready for you: the tab is the person's, its place among the open tabs kept, and nothing is told TailorIT. Only the time that wait began is kept with the run (the data inventory's row). Since the shell (SHELL-B), a job Filling whose tab no fill report shows for 90 seconds (its page turned to a document where no run starts: Autofill after page turn on Manually, a wall the grant does not take) is Ready for you too, the same way.

## Sign-up Information: the job-site password in this browser (jr6)

The owner's words of 2026-11-10 (docs/SPEC-AMENDMENTS.md §19): "you should store the password on localstorage on browser like jobright.ai. if needed, you should fetch this, and autofill it. user can set and manage the password on extension settings." The data inventory has each row.
- **What is kept, and where:** one email and one password for every job site, set by the person in the extension's own settings (the options page's Sign-up Information card, right after the connection, and Chrome's side panel's Settings section of that name). The password is encrypted with AES-GCM under a 256-bit key the worker makes once with extractable false and keeps in the extension origin's IndexedDB; the record (`signup:v1`: the email in the clear, the ciphertext with its 96-bit nonce, the time saved) is in `chrome.storage.local`, restricted to the extension's own contexts. Never in the settings, never synced, never in an export, never sent to TailorIT. The password must be 16 to 64 characters with an uppercase and a lowercase letter, a digit and one of `! @ # $ % ^ & * ( ) - _ = + ?`, and nothing else (no space, quote, backslash, `<` or `>`); "Generate strong password" makes a 20-character one with the browser's own random numbers (`crypto.getRandomValues`), never sent anywhere.
- **Who can reach it:** the worker, and the extension's own pages (the options page, Chrome's side panel), whose messages save, delete, import and read its status (`signup/save`, `signup/delete`, `signup/import`, `signup/status`: the status names whether one is saved, the email and when, never the password, and, while none is saved, an email to start the box with: the TailorIT profile's contact email (from the worker's memory, or, when it holds no profile, with one GET /profile as the card opens), else the account's as the worker already holds it; that email is shown on the extension's own pages alone). The panel on the page shows only whether one is saved and a link to the card: none of those messages is answered from it, nor from TailorIT's pages, and no job site's script reaches any of it. The fields and their words are in a part of the extension the panel on the page and the content script never load (check-build fails a build where they do). Once saved, the password is never shown again on any page; the card says to note it first.
- **When it is used:** decrypted by the worker only for the one answer that types it, to the one frame that asked (the tab's top frame, or the frame that draws an iCIMS portal's application), at a sign-in or create-account page, or a form's account section, on a host TailorIT's every-site sign-in covered (Workday's tenants, iCIMS's portals, Taleo, SuccessFactors' career hosts, Oracle Recruiting Cloud, SmartRecruiters, UltiPro, and ADP Workforce Now's and ClearCompany's candidate paths; the path read from Chrome's address, sent nowhere); never on a company's own page. An email gate is answered with the email alone, read from the record without decrypting. With Sign-in on Auto (which can be chosen only once a password is saved) or for one Autofill with Sign Up & Autofill, the form's Sign In or Create Account is pressed, once per tab, wall and host in 10 minutes. On Manual with a password saved, the email, the password and its confirmation are typed and the account's terms ticked, and the press is the person's (Jobright's account flow does the same): only in a tab shown to the person, never in the auto-apply agent's window, and kept in the form until the person presses, the run stops or ends, or the page goes (180 seconds at most after a press the site refused; in an application form's account section, until the person submits the form). A password longer than its box's own `maxlength` is never typed (since the jr6 integration fixes not decrypted either: the frame's ask carries the box's `maxlength` and, on a new-account form, the page's own rules, and the worker checks the saved password against them first, "The page's own password rules" below). While a typed password is kept, the browser's own submission of that form is held to a POST to the page's own origin. Every box it is typed into stays a password box to the extension whatever the page turns it into (a "Show password"), so it is never written over, nor captured as a submitted answer.
- **The import:** "Import from TailorIT", on the person's click, while none is saved here and the connection may read job-site sign-ins (`credentials:read`): one `GET /api/autofill/credentials?host=import.myworkdayjobs.com`, a tenant name no company uses, so TailorIT answers its every-site sign-in; taken only when it is for every site and its password meets the rules above (else nothing is saved). TailorIT records that host as the one it was last read for; nothing else is asked of it, and its own saved sign-ins are left as they are.
- **Deleting:** the card's Delete (it asks first: accounts made with that password then need the site's Forgot password) removes the record and the key; Sign-in on Auto goes back to Manual; any password still typed in a form for the person's press is emptied at once. A password whose key is gone (the site data cleared) cannot be read again and is removed; the card then says so.
- **At rest** (the jr6 review, sec-7): the encryption keeps the password from other extensions, the job sites' pages, sync, exports and a casual look at the extension's storage. It does not keep it from someone who can read the Chrome profile folder on this computer (local malware, a copy or backup of the profile, another account with access to its files): Chrome writes the key's structured clone, its bytes included, to the profile's IndexedDB unencrypted, beside the record, and its storage keeps old values until it compacts (Delete is no wipe). The stored ciphertext also shows the password's length (AES-GCM keeps lengths); since the jr6 integration fixes the worker reads that length for the page's rules (above), never logging, keeping or sending it. Chrome's own password manager uses the operating system's protection; this does not. The card's help says so, and suggests a password kept for job sites alone (a generated one).
- **The page's own password rules** (the shell, FIXPLAN §6.12 item 1): on a site's new-account form, Autofill reads the rules the page lists (Workday's "Password Requirements", iCIMS's create-login rules) and does not type a saved password the page would refuse (shorter than the page's own minimum, missing a kind of character it lists, or the same as the email): it types nothing on that form and says which rule, in its own words. Only whether each rule holds is checked; the password and its length are never logged or sent (the log names the rule's kind by number). Since the jr6 integration fixes (the review's SEC-1) the rules go with the frame's ask to the extension's own worker, as numbers and closed words only (the page's minimum, the kinds of character it requires, whether the password may equal the email, the smallest `maxlength` of its password boxes), and the worker checks the saved password against them without decrypting it: its length is read from the stored ciphertext, and every saved password already has each kind of character a page may ask for (the save requires them). A password they refuse is never decrypted, sent to the page's frame or counted as a press, so one saved after the toast is pressed by Sign Up & Autofill at once. The frame still checks the rules on what it is answered.
- **Account errors** (item 4): the page's error is read only for its kind (confirm the email, reset the password, a wrong email or password); its words are never kept or logged. A "verify your account" alert on arrival means nothing is typed or asked.
- **The wait for a password** (WD-04): with none saved, under Sign-in Auto or Sign Up & Autofill, the page waits up to 5 minutes for one to be saved in Sign-up Information, then tries the page once more; Cancel or Stop ends the wait; never in the auto-apply window.
- **Logs:** codes and flags only (`signup.key-made`, `.saved`, `.removed`, `.refused`, `.unreadable`, `.imported`, `.mode-reverted`; `signin.credential`; `signin.refused`, which names a refused rule by its place in a fixed list, or that the password does not fit the box), never an email, a password, its length, a host or a path.
- **Permissions:** none added (storage, IndexedDB and WebCrypto need none).

## Autofill on a page with no form: the site's Apply and the steps on the way (jr6)

The owner's words of 2026-11-10: "extension should also click `apply` to find and run the form ... and `Autofill` word will be kept" (docs/SPEC-AMENDMENTS.md §19). What it changes for the person's data:
- **The press:** the panel's Autofill (one word on every page of ours with no form, a confirmation and a submitted page aside) reads the page again first, then presses the site's own Apply as the person's click asks (the queue's Automatically and Run auto-apply take the same press), waiting a few seconds for one the page draws late, and the step the site shows next in the same page: the platform's declared choice (Workday's Apply Manually), or a dialog our press opened holding exactly one control in words such as "Apply manually" or "Continue as guest" (never "Autofill with Resume", "Use My Last Application", a sign-in, an account's creation or another site's profile). Consents on the way are pressed where a platform declares them, beside Taleo's Privacy Agreement and Jobvite's Data Consent "I Accept": ADP Workforce Now's "Consent & Continue" (never "Decline & Close"). A check that the person is human or a code the page shows first is the person's, and nothing is pressed; a sign-in or account page, before the press or after it, goes to the sign-in step ("Sign-up Information" above). Nothing is typed on the way but a Jobvite residence choice ("Jobvite's Data Consent" above) and a sign-in or email gate as their own rules say.
- **What is never pressed:** an Apply that would download a file, open a new tab or window (a link's or a form's target), or lead to another site (a link to another origin): the panel says why in one line, from a closed list of reasons (no Apply, which a download is told too; several; something needs you first; a new tab; another site; nothing opened), never page text or an address. A press that takes the tab to another site anyway ends the grant: Autofill does not go on there by itself (APPLYPLAN OQ3 and OQ4, defaults until the owner answers).
- **Following it:** a form the press draws in the same page is filled by the address's own platform rules; the next page in the same tab, on the same site and of the same application (or the one the press named on that origin), is started by the worker's grant ("Autofill's entry grant" in the data inventory), and a sign-in wall or a choice there gets one start of its own, three at most, each within a minute of the press or the step before it. What the frame tells the worker of a press is the destination's application key at most (a hash, never an address: `entry/pressed`), checked against the tab's application frame and Chrome's address for it; the panel's Cancel ends it.
- **Logs:** codes, numbers and flags only (`content.entry`, `content.entry-step`, `grant.armed`, `grant.step`, `grant.ended`, `queue.entry-timeout`), never an address, a host, a key, a label or a word of the page.

A site's email-first step before an application or a sign-in (iCIMS's gate, Oracle Recruiting Cloud's `…/apply/email`; BUILD D-d folds APPLYPLAN G into the shell's step). In every Sign-in mode, at a gate the platform's adapter declares:

The worker answers a gate with the email alone: the password is never decrypted for it, nor typed there.

- **Pressed:** the gate's Next only on Sign-in Auto or with Sign Up & Autofill, and never on a gate that asks for more than the email (its phone, a consent's scope), whose press stays the person's. The code the site then emails, and every check that the person is human, are never touched.

## What reaches an AI model

Only through the person's own TailorIT, which runs the Claude CLI, and only when the AI settings allow it:
- the visible text of a question and its visible options, to pick among them or to say what a question asks;
- for a pick, the profile's value for that question (a school, a degree, a field of study, a language, a referral source, or a custom answer). A value that names a sensitive topic or a sum is never sent, except that a school's, a degree's or a field of study's own name is checked for a sum only, since "Gender Studies" or "United States Military Academy" is just its name;
- for a draft (on by default since the owner's amendments, docs/SPEC-AMENDMENTS.md), the visible question, the posting's visible text on the form's own page (none for a form embedded in another site's page, and none in a dry run, which asks for no draft), the job's title and company, the words hidden page text asked AI tools to write (so TailorIT refuses a draft holding one), and which resume to draw on. TailorIT adds facts from the resume itself. A draft is written into the form; nothing is drawn on the page (until v4 it was marked as the AI's in the review, and waited for the person's confirmation while the "Wait for me to confirm each draft" setting was on; since v4 neither: docs/SPEC-AMENDMENTS.md §13 D6). No draft is asked for a box in a self-identification, legal, pay or consent context: under such a heading, revealed by such a question, following one up ("If yes, please explain"), or in a section of such questions only;
- for an AI answer (on by default since the owner's amendments), the same as a draft's, for a question nothing else settled: its visible label, hint, section and, for a choice, its visible options' clean labels by their places (since v5 Phase 2 a question nothing classified also asks its category in that same request, with the site's platform name; before, a classification of its own came first). TailorIT reads the facts itself from the resume and the profile's non-sensitive part (work history, education, languages, skills, job preferences), never the sensitive part, contact details, the name, the address or saved answers. An answer with nothing to go on is written as the AI's best guess (marked "AI guess" in the review until v4; marked nowhere since). The same screens keep every self-identification and consent question, and every box in such a context, from it, and so does a question about another person (an emergency contact, a referee, a manager or a spouse), an identifier (a number, an ID, a licence, a passport, a birth date), a postal address, a marketing or contact consent, an "I did not use AI" statement or a question whether AI wrote the application. Since jr6 the answers asked this way also cover, where the extension's rules leave them, how many years the person has in something and whether they have used a tool (the work entries and skills decide first), whether they are in a time zone or live or work in a country, a graduation and a high-school diploma, the visible question and options alone; and never a name prefix, a former name, an address's third line, a mailing address asked "if different", a Facebook profile or a site's numbered links, nor a draft for a box whose own words name another person (a reference);
- for the legal, pay and attention-check questions the profile does not answer (the owner's decision of 2026-11-01, docs/SPEC-AMENDMENTS.md §11: the AI answers mode All under Options › Modes, the default since v3 Phase 3 (before it, the setting "Let the AI answer legal, pay and attention-check questions your profile doesn't answer"), and only while AI answers are on): a work authorization, sponsorship (now, in the future or both), visa, citizenship or residence status, security clearance, export control, age or 18-or-over, criminal history (convictions, arrests, charges) or pay question, or an attention check ("select PURPLE to show you read this"), and since jr6 also OPT or CPT, military training, whether the person is bound by a non-compete or another restrictive agreement, and relatives at the employer (an answer to these three always marked an AI guess, whatever TailorIT's AI says it rests on, since no résumé or posting settles them; a job's essential functions, a disability's or an accommodation's topic, are never sent), as any AI answer: its visible label, hint, section and visible options, in TailorIT's `all` scope. Never the person's own answer: a question the profile answers is filled from it and never asked, and a question is asked only when the profile holds no answer (never while this browser may not read the sensitive part, where the person may hold one). TailorIT gives the most likely answer from the resume and the profile's non-sensitive part, a guess unless a fact settles it (marked "AI guess" until v4). An EEO option ("Woman", "Asian"), a self-identification or consent topic, an identity number, another person and an "I did not use AI" statement are never sent in this scope either, by the extension and again by TailorIT, and hidden page text never is: a question whose words only an aria-label or hidden text carries is never asked;
- for Edit with AI (the person's click on the button in a text box), the box's question and what it holds now (page text, which may be the person's own words), with the draft's context, so TailorIT rewrites it. A box whose text holds words hidden page text asked AI tools to write, names a sensitive topic or a sum, holds a self-identification answer or a decline ("Prefer not to say") on a line of its own, or holds an email address, a phone number, a link or a postal address, or (the audit of 2026-11-06) text addressed to AI tools, is never sent (the extension's screen, as TailorIT screens the same text). Since v3 Phase 3b the person may type what to change in its box ("Tell me what to add, change or improve", at most 750 characters), which goes with it as the question's instruction, screened the same way (an instruction naming a sensitive topic or stating a sensitive answer, a contact detail or a postal address is never sent, and the box says so). That box sits on the job page, in the extension's own closed part of it: what is typed there is typed on the page, so the page's own scripts can learn it as they learn any typing there. The extension stops the box's events from reaching the page's ordinary listeners, but a script that listens for every event on the window or the document in the capture phase still hears, besides each key (keydown and keyup), the text each keystroke enters (textInput, beforeinput and input carry it), anything pasted or dropped into the box (paste, drop) and what an input method composes (composition events). Since the audit of 2026-11-06 the page's ordinary (bubbling) listeners hear none of these. A person who would rather not have the page see an instruction can use the side panel's custom question instead (since v5 Phase 1 in Chrome's side panel: the panel on the page's custom question is typed on the page too, "The panel on the page"). Since v5 Phase 1 the button shows only on text boxes at least 40 px tall. The words are never kept;

- for a cover letter (Phase G; since v3 Phase 3b a cover-letter text box as well as an upload), when a form has a cover-letter upload and the person has no letter for the job, or (until v4, which removed the button and the card's row) when they choose Write it now on the job card: the job's title and company (TailorIT's, or the page title's when TailorIT lacks the job), the posting's visible text on the form's own page (none for a form inside another site's page, never TailorIT's stored copy), the words hidden page text asked AI tools to write (TailorIT keeps no letter holding one), and which resume to draw on. TailorIT's cover-letter AI writes it from that resume into the person's Cover Letters. Only while AI-written answers (the "Draft open answers" setting) are on, never in a dry run (the card offers no Write it now there), never when the form's page cannot be read, and never on a posting that says AI is not allowed in profile-only mode or a form that states "I did not use AI", where only a letter the person wrote or edited is attached. Every ask first checks whether the person has a letter, and only a fill or Write it now that may have one written, finding none, sends the posting text. Asking whether the person has a letter (every ask's first step, a dry run, the card's row, a profile-only fill, and the upload after the extension's worker restarted) sends the job (TailorIT's, or the page title's company and title when TailorIT lacks it) and the resume only: no posting text, no canaries, and nothing is written;

- for a custom question the person types in the side panel (v2), their question, the posting's visible text on the form's own page (none for a form inside another site's page), the job's title and company, the words hidden page text asked AI tools to write, and which resume to draw on (the one the job card attaches, or the one chosen with Change); TailorIT adds facts from that resume. A question about self-identification, work authorization, sponsorship, pay or consent, or one that checks the person read the form, is never sent, by the extension and again by TailorIT.

- for the job's known questions at the run's start (v1.3, the run-start batch): each question TailorIT keeps for the job that the profile and an earlier answer leave open, on any step (never an upload), as any AI answer: its label and options, quoted as untrusted, through the same screens, the sensitive part never read for it. Such a question's words may come from another person's application to the same job, captured from its visible label, or from the site's public board (Greenhouse's). Never an earlier answer: a field an earlier application fills asks no AI;

- for an answer TailorIT prepared for the job ahead of time (v1.5, Prebuild), nothing from the extension: a field a ready one fills asks no AI, and TailorIT made it on its own side (by its AI, or the person's own AI through its MCP server), in no request of the extension's. A not-ready one's question goes to the AI as any open question does, under the rules above;

- for tailoring (v1.4; only on the person's click on Tailor Resume For This Job or Generate Cover Letter, only while AI-written answers are on, never on a posting that says AI is not allowed or a form that states "I did not use AI" unless the person chose Use AI anyway, nor after the tab's run went profile-only): the job (for a job TailorIT has, TailorIT's own copy of it; else the posting's visible text on the form's page, its company and title as the page's title names them, and the page's canaries, so TailorIT keeps nothing holding one) and which resume to draw on. TailorIT's tailoring gives Claude that resume and the job, writes the tailored resume (and with Generate Cover Letter the letter) on the profile's templates, and keeps them. Nothing of the form is sent.

Edit with AI and the custom question run only when the person asks (their click on Edit with AI, or Get answer), and only while AI-written answers (the "Draft open answers" setting) are on: with it off, Edit with AI is not offered, the custom question box is disabled with the reason, and the worker refuses either if asked. A custom question still works on a posting that says AI is not allowed, since the person asked; the side panel shows that posting's notice above it, and with the answer.

Never: self-identification (EEO) answers, work authorization, sponsorship, criminal record, pay, consent, contact details, hidden page text, the answers of an application the person submitted (v1.3), or TailorIT's stored copy of a posting (but for tailoring, v1.4, where TailorIT writes from its own copy of a job it has). Never, in any scope (the audit of 2026-11-06): a check that the person is human or a CAPTCHA asked as a question ("Are you a robot?", "What is 4 + 3?", "Enter the characters you see"), a question or statement about how the application was made (whether AI such as Claude or ChatGPT, automation, an autofill, an extension or someone's help was used), and a binding waiver or covenant (arbitration, a jury-trial or class-action waiver, a non-compete, a release of claims), asked for the person's agreement (since jr6 whether they are already bound by a non-compete, asked as a fact, is one of the legal questions above). Questions that look like self-identification or consent questions, by their words, their hint, their section's heading or their options, are screened out before classification, a draft or an answer, by the extension and again by TailorIT; so are legal, criminal-history, pay and attention-check questions, but for the AI answer above while its setting is on.

When a posting says AI-assisted applications are not allowed, or its form asks the person to confirm they did not use AI, the default ("Fill from my profile only", the owner's amendments) sends nothing at all to the AI for that run: no pick, classification, draft or answer, and Edit with AI is not offered. A run that learns it only on a later pass gives up what it was still waiting for from the AI and writes none of it, and the worker asks the AI nothing more for that run. The other choice is "Use AI anyway" ("Ask me each time", the policy card, until v4: settings version 6 reads it as profile only). Since the snapshot build of 2026-11-06 a form's "I did not use AI" statement is found even past a label's first 300 characters (a long AI policy ending in one): the whole visible label stays in the page's frame, and only a flag that it holds such a statement goes to the worker, beside the usual 300-character label.
